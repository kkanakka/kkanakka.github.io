## Answering a Kubernetes probe

<!-- DIAGRAM:sequence:END -->
<details class="ic-probe"><summary><span class="ic-tag">K8S-01</span>A pod is in CrashLoopBackOff. Walk me through it.</summary><div class="ic-answer"><p><code>kubectl logs --previous</code> for the dying container's output; <code>describe</code> for the last exit code and reason (137 OOMKilled, 1 app error, 127 missing binary) and for probe-kill events; check <code>CreateContainerConfigError</code> for missing ConfigMap/Secret keys and whether <code>command</code>/<code>args</code> override the entrypoint; then reproduce with <code>kubectl debug --copy-to</code> and a sleep command. Say that backoff caps at five minutes and resets after ten minutes of healthy running.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">K8S-02</span>What does a CPU limit do, and why can it hurt a service whose average CPU is 30%?</summary><div class="ic-answer"><p>It becomes a CFS quota: <code>cpu.max</code> allows N ms of CPU per 100 ms period; bursts beyond that are throttled until the next period, regardless of idle cores. A bursty request handler or a runtime with many threads consumes the quota in a few milliseconds and then stalls, so p99 latency climbs while the average looks fine. Check <code>container_cpu_cfs_throttled_periods_total</code>. Raise or remove the limit, or align thread counts with the quota.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">K8S-03</span>Memory limit versus request: what happens when each is exceeded?</summary><div class="ic-answer"><p>Exceeding the limit triggers the cgroup OOM killer: the container exits 137, reason <code>OOMKilled</code>, and the kubelet restarts it. Exceeding the request is fine until the node runs short on memory; then the kubelet's eviction ranks pods by usage over request (and QoS), and evicts the worst offenders, which shows as <code>Evicted</code> status, not OOMKilled.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">K8S-04</span>A rolling update causes a burst of 502s although readiness probes pass. Why, and what's the fix?</summary><div class="ic-answer"><p>Endpoint removal and SIGTERM happen in parallel, so the proxy keeps sending traffic for a few seconds after the container starts shutting down. Add a <code>preStop</code> sleep of several seconds, make <code>terminationGracePeriodSeconds</code> exceed preStop plus drain time, make the app drain on SIGTERM (and ensure it's PID 1 or receives the signal), and send <code>Connection: close</code> or GOAWAY to keep-alive clients.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">K8S-05</span>How does traffic to a ClusterIP reach a pod if the IP is on no interface?</summary><div class="ic-answer"><p>kube-proxy programs DNAT rules (iptables, IPVS, or nftables) on every node mapping VIP:port to the set of ready pod IPs from the Service's EndpointSlices; the kernel rewrites the destination on the first packet of a connection and conntrack keeps the mapping. Because it's per connection, long-lived connections stick to one pod.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">K8S-06</span>Why does a StatefulSet pod on a dead node not move automatically?</summary><div class="ic-answer"><p>Kubernetes can't tell a partitioned node from a dead one, and a StatefulSet guarantees at most one pod per identity because two instances writing the same volume would corrupt data. The pod stays <code>Terminating</code>/<code>Unknown</code> until the node object is deleted, the pod is force-deleted (after you've confirmed the old node is really gone or fenced), or a node fencing mechanism does it.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">K8S-07</span>You updated a ConfigMap but the app still uses old values.</summary><div class="ic-answer"><p>Environment variables from ConfigMaps never update; volume mounts update within roughly a minute unless mounted via <code>subPath</code>, which never updates; and the app may read config only at startup. Trigger a rollout (hash the ConfigMap into a pod annotation) or implement reload on change.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">K8S-08</span>Pods in a cluster intermittently take exactly five seconds to resolve names.</summary><div class="ic-answer"><p>Classic conntrack race on parallel A/AAAA UDP queries, or an overloaded CoreDNS. Five seconds is the resolver timeout before retry. Mitigate with NodeLocal DNSCache, <code>dnsConfig.options: single-request-reopen</code>, use-vc (TCP), scaling CoreDNS with the cluster, and lowering <code>ndots</code> or using FQDNs to cut query volume.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">K8S-09</span>A node goes NotReady. What happens to its pods and what do you check?</summary><div class="ic-answer"><p>The node controller taints it <code>unreachable</code>/<code>not-ready</code> with NoExecute; pods tolerate it for 300 s by default, then are evicted and Deployments reschedule them elsewhere (StatefulSets wait). On the node: kubelet and containerd journals, disk space under <code>/var/lib/kubelet</code>, memory/PID pressure, certificate validity, API server reachability; from the control plane: node conditions and heartbeat age. Meanwhile, ensure remaining capacity can absorb the pods.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">K8S-10</span>Why can a PodDisruptionBudget block a cluster upgrade, and what doesn't it protect against?</summary><div class="ic-answer"><p>Drain uses the eviction API, which refuses evictions that would violate the PDB; a PDB requiring all replicas available, or a Deployment with one replica and <code>minAvailable: 1</code>, blocks every drain. PDBs don't apply to node crashes, kernel OOM kills, or deleting the pod directly, only to voluntary disruptions.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">K8S-11</span>etcd is at its space quota and the cluster is read-only. Recover it.</summary><div class="ic-answer"><p><code>etcdctl alarm list</code> shows NOSPACE; compact to the latest revision (<code>etcdctl compact &lt;rev&gt;</code>), defragment each member in turn, then <code>etcdctl alarm disarm</code>. Find what filled it (events churn, a controller writing huge objects, no auto-compaction) and fix it; consider raising <code>--quota-backend-bytes</code> modestly. Take a snapshot before you start.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">K8S-12</span>Nothing in the cluster can be created; the API server returns "failed calling webhook."</summary><div class="ic-answer"><p>A validating or mutating webhook with <code>failurePolicy: Fail</code> is unreachable (its pods are down, its Service has no endpoints, or its certificate expired). Temporarily set the policy to <code>Ignore</code> or delete the webhook configuration to restore the cluster, then fix the webhook. Design: exclude <code>kube-system</code>, set short <code>timeoutSeconds</code>, run webhook replicas across zones, and don't let the webhook gate its own namespace.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">K8S-13</span>The HPA shows "unknown" for targets and never scales.</summary><div class="ic-answer"><p>No metrics: metrics-server is missing or unhealthy, or the pods have no CPU requests so utilization is undefined. Fix metrics-server (check <code>kubectl top pod</code>), set requests, and confirm the HPA's target reference matches the Deployment name and that custom metrics adapters are serving.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">K8S-14</span>Why do long-lived gRPC connections leave new pods idle after scaling out?</summary><div class="ic-answer"><p>Services balance at connection setup (DNAT per connection), so existing HTTP/2 connections stay pinned to old pods. Options: client-side load balancing against a headless Service, a service mesh or L7 proxy that balances requests, server-side <code>MAX_CONNECTION_AGE</code> to force periodic reconnects, or a proxy like Envoy in front.</p></div></details>
