## How it works

<img src="/diagrams/ch10/sequence.svg" alt="How it works" class="doc-diagram doc-diagram-seq" />

<!-- DIAGRAM:sequence:END -->
<p class="gm-lead">Inference has two phases with completely different hardware profiles: <strong>prefill</strong> (read the whole prompt at once — compute-bound) and <strong>decode</strong> (produce one token at a time — memory-bandwidth-bound). Every serving trick exists to keep both phases busy on the same GPU.</p>

## The four numbers that describe serving performance

<dl class="gm-kv">
<dt>TTFT</dt><dd>Time to first token. Dominated by prefill = prompt length × model size ÷ compute. Also includes queueing and network.</dd>
<dt>ITL / TPOT</dt><dd>Inter-token latency (time per output token). Dominated by decode bandwidth. What "feels fast" when streaming.</dd>
<dt>Throughput</dt><dd>Tokens per second across all users on a GPU. Rises with batch size until compute-bound or memory-full.</dd>
<dt>Goodput</dt><dd>Throughput that meets latency SLOs. The real metric operators optimize.</dd>
</dl>

## Techniques that make inference affordable

<div class="gm-grid2">
<div class="gm-card"><b>Continuous batching</b>Instead of waiting for a batch of requests to all finish, the scheduler injects new requests into the batch at every decode step as old ones finish. Raises GPU utilization 5–20× over static batching. Every modern server (vLLM, TensorRT-LLM, SGLang, TGI) does this.</div>
<div class="gm-card"><b>PagedAttention</b>The KV cache is allocated in fixed-size blocks (like OS virtual memory pages) instead of one contiguous reserved region per request. Eliminates fragmentation, lets many more requests share a GPU, and lets requests share cache blocks for common prefixes.</div>
<div class="gm-card"><b>Prefix / prompt caching</b>If two requests start with the same tokens (a shared system prompt, an earlier turn of the same chat, a long document), the KV cache for that prefix is reused instead of recomputed. Cuts TTFT and cost dramatically for chat and agent workloads. Exposed to API users as "prompt caching" with a cheaper price for cache hits.</div>
<div class="gm-card"><b>Speculative decoding</b>A small "draft" model guesses the next k tokens; the big model verifies all k in one forward pass (which costs about the same as one token, since decode is bandwidth-bound). Accepted tokens are free. 2–3× decode speedup with identical output distribution.</div>
<div class="gm-card"><b>Quantization</b>Store weights in INT8/FP8/INT4. Halves or quarters the bytes read per token → proportionally faster decode and more KV room. KV cache itself can be quantized to FP8.</div>
<div class="gm-card"><b>Disaggregated prefill/decode</b>Run prefill on one GPU pool (compute-heavy, needs H100s) and decode on another (bandwidth-heavy, can use more memory-per-dollar hardware), transferring the KV cache between them over NVLink/RDMA. Removes the interference where a long prefill stalls everyone else's decode.</div>
<div class="gm-card"><b>Tensor parallelism at inference</b>Split each layer across 2–8 GPUs in a node so the aggregate HBM bandwidth (and capacity) serves one model. Decode reads weights from 8 GPUs at once → ~8× faster per step, with an all-reduce per layer over NVLink.</div>
<div class="gm-card"><b>CUDA graphs and fused kernels</b>Capture the whole decode step as one graph to remove per-kernel launch overhead; fuse norm + matmul + activation to avoid HBM round-trips.</div>
</div>

## Sizing a deployment (worked example)

<p>Serve a 70B BF16 model with 4k-token average context on H100s at an ITL target of 30 ms:</p>
<ul>
<li>Weights: 140 GB → needs TP across 2 GPUs (160 GB) at minimum; TP=4 leaves ~180 GB for KV cache.</li>
<li>KV per request: 4k × 327 KB ≈ 1.3 GB → ~130 concurrent requests fit in 180 GB.</li>
<li>Decode step: ~140 GB of weights ÷ (4 × 3.35 TB/s) ≈ 10 ms + KV reads + all-reduce ≈ 20–25 ms. Within target.</li>
<li>Throughput ≈ 130 requests ÷ 0.025 s ≈ 5,000 tokens/s per 4-GPU replica. Prefill for a 4k prompt ≈ 4k × 140 GFLOP ÷ (4 × ~600 TFLOPS effective) ≈ 0.25 s TTFT.</li>
</ul>
