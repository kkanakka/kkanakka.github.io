## A plausible core schema

<pre><code><span class="gm-c">-- Simplified; real systems shard by org_id or conversation_id</span>
<span class="gm-k">CREATE TABLE</span> organizations (id uuid <span class="gm-k">PRIMARY KEY</span>, name text, plan text, created_at timestamptz);
<span class="gm-k">CREATE TABLE</span> users (id uuid <span class="gm-k">PRIMARY KEY</span>, org_id uuid, email text, settings jsonb);
<span class="gm-k">CREATE TABLE</span> conversations (
  id uuid <span class="gm-k">PRIMARY KEY</span>, user_id uuid, project_id uuid <span class="gm-k">NULL</span>,
  title text, model text, system_prompt_ref text,
  created_at timestamptz, updated_at timestamptz, deleted_at timestamptz
);
<span class="gm-k">CREATE TABLE</span> messages (
  id uuid <span class="gm-k">PRIMARY KEY</span>, conversation_id uuid, parent_id uuid <span class="gm-k">NULL</span>,   <span class="gm-c">-- parent_id enables edit/regenerate branches</span>
  role text, content jsonb,             <span class="gm-c">-- array of blocks: text, image, tool_use, tool_result</span>
  input_tokens int, output_tokens int, stop_reason text, created_at timestamptz
);
<span class="gm-k">CREATE TABLE</span> attachments (id uuid, message_id uuid, object_key text, mime text, extracted_text_key text);
<span class="gm-k">CREATE TABLE</span> memories (id uuid, user_id uuid, kind text, content text, embedding vector(1024), source_conversation_id uuid);
<span class="gm-k">CREATE TABLE</span> usage_events (id bigserial, org_id uuid, model text, input_tokens int, cached_tokens int, output_tokens int, ts timestamptz);</code></pre>
<p>Two details matter: messages form a <em>tree</em> (each message points to its parent) so that "edit and resend" and "regenerate" create branches instead of destroying history; and content is a list of typed blocks, not a string, so tool calls, images and files sit in the same timeline as text.</p>

## Files and documents

<ol>
<li>Client uploads directly to object storage via a presigned URL (the app server never proxies the bytes).</li>
<li>A worker extracts text/tables (PDF parsers, OCR) and for images produces the resized bytes the vision model accepts.</li>
<li>Extracted text is inserted into the prompt for the current turn (small files) or chunked, embedded and stored in the vector index for retrieval (large project knowledge bases).</li>
<li>Virus scanning and MIME validation happen before anything reaches the model or a sandbox.</li>
</ol>

## Observability stack

<ul>
<li><strong>Metrics</strong> (Prometheus/Mimir): request rate, TTFT/ITL histograms, queue depth, KV utilization, DCGM GPU metrics (Chapter 22), error rates by model.</li>
<li><strong>Traces</strong> (OpenTelemetry → Jaeger/Tempo): one trace per request across edge → app → gateway → engine, so a slow response can be attributed to queueing vs prefill vs DB.</li>
<li><strong>Logs</strong>: structured JSON, sampled; prompt contents are usually redacted or held in a separate access-controlled store with short retention.</li>
</ul>
