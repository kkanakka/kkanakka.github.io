## Exposing RDMA to pods

<pre><code><span class="gm-c"># With the NVIDIA Network Operator installed: request an RDMA device + SR-IOV VF</span>
apiVersion: v1
kind: Pod
spec:
  containers:
  - name: rdma-training
    resources:
      limits:
        nvidia.com/gpu: <span class="gm-s">8</span>
        rdma/rdma_shared_device_a: <span class="gm-s">1</span>        <span class="gm-c"># shared-device plugin, or</span>
        nvidia.com/hostdev: <span class="gm-s">8</span>                <span class="gm-c"># SR-IOV VFs, one per GPU (name varies by config)</span>
    securityContext:
      capabilities:
        add: [<span class="gm-s">"IPC_LOCK"</span>]                   <span class="gm-c"># required to pin memory for RDMA</span>
    env:
    - {name: NCCL_IB_HCA,     value: <span class="gm-s">"mlx5"</span>}
    - {name: NCCL_SOCKET_IFNAME, value: <span class="gm-s">"eth0"</span>}
    - {name: NCCL_DEBUG,      value: <span class="gm-s">"INFO"</span>}    <span class="gm-c"># first run only: confirm "NET/IB" not "NET/Socket"</span>
    - {name: NCCL_IB_DISABLE, value: <span class="gm-s">"0"</span>}

<span class="gm-c"># Host networking is the blunt alternative — full NIC access, no CNI overhead, but pods share the host port space</span>
spec:
  hostNetwork: <span class="gm-k">true</span>
  dnsPolicy: ClusterFirstWithHostNet</code></pre>

## Network policy for a training job

<pre><code>apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: gpu-training-netpol
spec:
  podSelector:
    matchLabels: {app: distributed-training}
  policyTypes: [Ingress, Egress]
  ingress:
  - from:
    - podSelector:
        matchLabels: {app: distributed-training}
    ports:
    - {protocol: TCP, port: 29500}      <span class="gm-c"># torch.distributed rendezvous (MASTER_PORT)</span>
    - {protocol: TCP, port: 23456}      <span class="gm-c"># example NCCL socket port; NCCL actually uses a dynamic range</span>
  egress:
  - to:
    - podSelector:
        matchLabels: {app: distributed-training}</code></pre>
<div class="gm-note"><b>Bandwidth annotations</b><code>kubernetes.io/ingress-bandwidth</code> and <code>kubernetes.io/egress-bandwidth</code> only work with CNIs that implement the bandwidth plugin (e.g. Calico with it enabled), and shape only the pod network — not RDMA or host-network traffic.</div>

## NVMe storage

<table>
<tbody><tr><th></th><th>SATA SSD</th><th>NVMe (PCIe 4)</th><th>NVMe RAID0 ×4</th><th>Network FS / object store</th></tr>
<tr><td>Sequential read</td><td>~500 MB/s</td><td>~7 GB/s</td><td>~25 GB/s</td><td>0.1–5 GB/s</td></tr>
<tr><td>Random 4k IOPS</td><td>~100k</td><td>~1M</td><td>~3M</td><td>low, ms latency</td></tr>
<tr><td>Latency</td><td>~100 µs</td><td>~20–80 µs</td><td>~20–80 µs</td><td>1–50 ms</td></tr>
<tr><td>Role</td><td>OS disk</td><td>dataset cache, checkpoints</td><td>hot shard cache for large jobs</td><td>source of truth</td></tr>
</tbody></table>
<pre><code><span class="gm-c"># Local NVMe as a Kubernetes volume (local PV; use the local-static-provisioner in practice)</span>
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata: {name: nvme-local}
provisioner: kubernetes.io/no-provisioner
volumeBindingMode: WaitForFirstConsumer
---
apiVersion: v1
kind: PersistentVolume
metadata: {name: nvme-node07}
spec:
  capacity: {storage: 2Ti}
  accessModes: [ReadWriteOnce]
  persistentVolumeReclaimPolicy: Delete          <span class="gm-c"># local disks are scratch; Retain only if you manage cleanup</span>
  storageClassName: nvme-local
  local: {path: /mnt/nvme-raid0}
  nodeAffinity:
    required:
      nodeSelectorTerms:
      - matchExpressions:
        - {key: kubernetes.io/hostname, operator: In, values: [gpu-node-07]}</code></pre>
<pre><code><span class="gm-c"># Building the RAID0 scratch volume on the node</span>
mdadm --create /dev/md0 --level=0 --raid-devices=4 /dev/nvme0n1 /dev/nvme1n1 /dev/nvme2n1 /dev/nvme3n1
mkfs.ext4 -F -E stride=128,stripe-width=512 /dev/md0
mount -o noatime,nodiratime /dev/md0 /mnt/nvme-raid0</code></pre>
<div class="gm-danger"><b>Correction to the original guide</b>The original mount line used <code>data=writeback,barrier=0,nobh</code>. <code>barrier=0</code> disables write barriers, so a power loss or node crash can corrupt the filesystem, including checkpoints you were counting on; <code>nobh</code> was removed from ext4 years ago and is ignored. On modern NVMe, <code>noatime</code> alone gets essentially all the throughput. Keep barriers on. RAID0 itself is fine for scratch because any single-drive failure loses the array — never put the only copy of anything on it.</div>

## Pod layout for fast data access

<pre><code>spec:
  containers:
  - name: ml-training
    volumeMounts:
    - {name: nvme-scratch, mountPath: /data}       <span class="gm-c"># dataset shards synced from S3 at start</span>
    - {name: ram-cache,    mountPath: /tmp/cache}  <span class="gm-c"># decoded batches, tiny hot files</span>
    - {name: ckpt,         mountPath: /ckpt}       <span class="gm-c"># checkpoints → NVMe, then async upload</span>
  volumes:
  - name: nvme-scratch
    persistentVolumeClaim: {claimName: nvme-pvc}
  - name: ram-cache
    emptyDir: {medium: Memory, sizeLimit: 8Gi}     <span class="gm-c"># counts against the pod's memory limit</span>
  - name: ckpt
    persistentVolumeClaim: {claimName: nvme-pvc}</code></pre>
<ul>
<li>Sync datasets to local NVMe once per node (init container with <code>aws s3 sync</code> / <code>rclone</code>), not per pod restart if the node is reused.</li>
<li>Write checkpoints locally then upload asynchronously; never block the training loop on object-storage latency.</li>
<li>For shared read-heavy datasets across many nodes, a parallel filesystem (Lustre, GPFS, Weka) or a caching layer (Alluxio, JuiceFS) in front of object storage beats each node re-downloading.</li>
</ul>
