<p class="gm-lead">The three incident patterns from the original guide — resource contention, disk exhaustion, driver faults — are the three that recur everywhere. This chapter keeps the analysis, replaces the fragile fixes with durable ones, and adds the isolation and emergency procedures that prevent recurrence.</p>

## Incident pattern 1 — Resource contention

<p><strong>What happened:</strong> a test application ("feedring") co-scheduled on production inference nodes consumed disk and CPU during startup; the latency-sensitive GPU service saw CPU interrupt storms, memory pressure and GPU memory spikes. <strong>Root cause:</strong> no isolation between workload classes.</p>

<p>Also reserve node resources for the OS so daemons never fight pods: kubelet <code>systemReserved</code>/<code>kubeReserved</code> plus <code>evictionHard</code> thresholds for memory and disk.</p>

## Incident pattern 2 — Disk exhaustion

<p><strong>What happened:</strong> large uncompressed logs filled the node's local disk; the kubelet hit DiskPressure, evicted pods, and the node needed manual cleanup. <strong>Root cause:</strong> no log rotation, no image garbage collection tuning, no disk alerts.</p>
<div class="gm-danger"><b>Correction to the original guide</b>The original fix was a privileged DaemonSet running <code>find /var/log/pods -delete</code> and <code>docker system prune</code> every hour. It deletes logs out from under the kubelet (breaking <code>kubectl logs</code>), assumes Docker on nodes that almost certainly run containerd, and mounts the Docker socket cluster-wide — a root-equivalent privilege. Kubernetes already has the mechanisms; configure them instead.</div>
<pre><code><span class="gm-c"># kubelet configuration — the built-in fixes</span>
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
containerLogMaxSize: <span class="gm-s">"50Mi"</span>        <span class="gm-c"># rotate each container log at 50 MiB</span>
containerLogMaxFiles: 5            <span class="gm-c"># keep 5 rotated files (compressed by kubelet)</span>
imageGCHighThresholdPercent: 80    <span class="gm-c"># start deleting unused images at 80% disk</span>
imageGCLowThresholdPercent: 60     <span class="gm-c"># stop at 60%</span>
imageMinimumGCAge: <span class="gm-s">"12h"</span>
evictionHard:
  nodefs.available: <span class="gm-s">"10%"</span>
  imagefs.available: <span class="gm-s">"15%"</span>
evictionSoft:
  nodefs.available: <span class="gm-s">"15%"</span>
evictionSoftGracePeriod:
  nodefs.available: <span class="gm-s">"2m"</span></code></pre>
<pre><code><span class="gm-c"># Per-pod ephemeral storage limits: a chatty pod is evicted, not the whole node</span>
resources:
  requests: {ephemeral-storage: <span class="gm-s">"10Gi"</span>}
  limits:   {ephemeral-storage: <span class="gm-s">"20Gi"</span>}

<span class="gm-c"># Namespace guard rail</span>
apiVersion: v1
kind: LimitRange
metadata: {name: ephemeral-defaults, namespace: ml-training}
spec:
  limits:
  - type: Container
    default: {ephemeral-storage: <span class="gm-s">"20Gi"</span>}
    defaultRequest: {ephemeral-storage: <span class="gm-s">"5Gi"</span>}</code></pre>
<pre><code><span class="gm-c"># Alerts (node-exporter)</span>
- alert: NodeDiskWillFillIn6h
  expr: predict_linear(node_filesystem_avail_bytes{mountpoint=<span class="gm-s">"/"</span>}[1h], 6*3600) &lt; 0
  for: 30m
  labels: {severity: warning}
- alert: NodeDiskPressure
  expr: kube_node_status_condition{condition=<span class="gm-s">"DiskPressure"</span>,status=<span class="gm-s">"true"</span>} == 1
  labels: {severity: critical}</code></pre>
<ul>
<li>Ship logs off-node (Fluent Bit / Vector → Loki / Elasticsearch) so local disk is a buffer, not an archive.</li>
<li>Training code should write checkpoints and TensorBoard logs to the NVMe scratch PV, never to the container's writable layer.</li>
<li>Set <code>emptyDir.sizeLimit</code> on every emptyDir; unbounded emptyDirs on the root disk are the other classic filler.</li>
</ul>

## Incident pattern 3 — GPU driver faults

<p><strong>What happened:</strong> a specific NVIDIA driver version on A100s produced ERR states in <code>nvidia-smi</code> and utility outages; no staging test had caught it; nothing degraded gracefully. <strong>Root cause:</strong> unpinned driver versions rolled straight to production, no automated GPU health gating.</p>
<div class="gm-warn"><b>Correction to the original guide</b>The original sidecar ran <code>kill -TERM 1</code> — which, in a Kubernetes pod without <code>shareProcessNamespace</code>, kills the sidecar's own PID 1 (itself), not the main container. It also required <code>/dev</code> mounted from the host. Health gating belongs at the node level, where a bad GPU can be taken out of rotation for every pod, not in each pod.</div>
<pre><code><span class="gm-c"># 1. Pin versions via the GPU Operator ClusterPolicy; upgrade a canary pool first</span>
apiVersion: nvidia.com/v1
kind: ClusterPolicy
metadata: {name: cluster-policy}
spec:
  driver:
    version: <span class="gm-s">"550.127.05"</span>          <span class="gm-c"># explicit — never "latest"</span>
    upgradePolicy:
      autoUpgrade: <span class="gm-k">true</span>
      maxParallelUpgrades: 1
      drain: {enable: <span class="gm-k">true</span>, timeoutSeconds: 600}
      podDeletion: {force: <span class="gm-k">false</span>}
    <span class="gm-c"># target the canary pool with nodeSelector first, then widen</span>

<span class="gm-c"># 2. Node-level health: the device plugin already un-advertises GPUs on Xid 79/48 etc.</span>
<span class="gm-c">#    Add a DaemonSet that runs `dcgmi diag -r 1` on a schedule and cordons on failure:</span>
<span class="gm-c">#    Node Problem Detector with a custom plugin, or the GPU Operator's node-status-exporter.</span>

<span class="gm-c"># 3. Readiness in the workload: fail readiness (not the whole pod) when the GPU is unhealthy</span>
readinessProbe:
  exec:
    command: [<span class="gm-s">"sh"</span>, <span class="gm-s">"-c"</span>, <span class="gm-s">"nvidia-smi --query-gpu=name --format=csv,noheader &gt;/dev/null &amp;&amp; curl -sf localhost:8000/health"</span>]
  periodSeconds: 15
  failureThreshold: 3</code></pre>
<pre><code><span class="gm-c"># Manual triage on a suspect node</span>
dmesg -T | grep -i -E <span class="gm-s">"xid|nvrm"</span>          <span class="gm-c"># Xid codes: 79 fell off bus, 48/63/64 ECC, 31/43 app fault, 13 graphics exception</span>
nvidia-smi -q -d ERR,ECC,PAGE_RETIREMENT,ROW_REMAPPER
dcgmi diag -r 2                          <span class="gm-c"># medium diagnostic (~2 min); -r 3 is long</span>
nvidia-smi --gpu-reset -i 0              <span class="gm-c"># only after all processes using GPU 0 are gone; not supported on all boards</span>
<span class="gm-c"># If ROW_REMAPPER shows pending remaps or ECC DBE &gt; 0: cordon, drain, RMA</span></code></pre>

## Emergency response

<pre><code><span class="gm-c"># Take a GPU node out of service</span>
kubectl cordon gpu-node-01
kubectl drain gpu-node-01 --ignore-daemonsets --delete-emptydir-data --grace-period=120 --timeout=600s

<span class="gm-c"># Cluster GPU inventory at a glance</span>
kubectl get nodes -l nvidia.com/gpu.present=true \
  -o custom-columns=NAME:.metadata.name,GPUS:.status.allocatable.nvidia\.com/gpu,READY:.status.conditions[?\(@.type==\"Ready\"\)].status

<span class="gm-c"># Which pods hold GPUs</span>
kubectl get pods -A -o json | jq -r <span class="gm-s">'.items[] | select(.spec.containers[].resources.limits."nvidia.com/gpu" != null) | "\(.metadata.namespace)/\(.metadata.name) \(.spec.nodeName)"'</span>

<span class="gm-c"># Clean up finished pods that still count against quota</span>
kubectl delete pods --field-selector=status.phase=Failed -n gpu-namespace
kubectl delete pods --field-selector=status.phase=Succeeded -n gpu-namespace

<span class="gm-c"># Reset a GPU on a node (run ON the node via SSH or a privileged debug pod — kubectl exec cannot target a Node object)</span>
kubectl debug node/gpu-node-01 -it --image=nvcr.io/nvidia/cuda:12.4.1-base-ubuntu22.04 -- chroot /host nvidia-smi --gpu-reset -i 0</code></pre>
<div class="gm-warn"><b>Correction to the original guide</b>The original emergency script looped <code>kubectl exec -it $node -- nvidia-smi --gpu-reset</code> over Node objects. <code>kubectl exec</code> only works on pods; use <code>kubectl debug node/…</code> or SSH. And a GPU reset while any process still holds the device fails or hangs — drain first.</div>

## Quotas and limit ranges (guard rails for shared clusters)

<pre><code>apiVersion: v1
kind: ResourceQuota
metadata: {name: gpu-training-quota, namespace: ml-training}
spec:
  hard:
    requests.nvidia.com/gpu: <span class="gm-s">"32"</span>
    requests.cpu: <span class="gm-s">"256"</span>
    requests.memory: <span class="gm-s">"2Ti"</span>
    requests.storage: <span class="gm-s">"20Ti"</span>
    persistentvolumeclaims: <span class="gm-s">"20"</span>
    count/pods: <span class="gm-s">"100"</span>
---
apiVersion: v1
kind: LimitRange
metadata: {name: gpu-training-limits, namespace: ml-training}
spec:
  limits:
  - type: Container
    defaultRequest: {cpu: <span class="gm-s">"2"</span>, memory: <span class="gm-s">"4Gi"</span>}
    default:        {cpu: <span class="gm-s">"2"</span>, memory: <span class="gm-s">"4Gi"</span>}     <span class="gm-c"># default == defaultRequest → Guaranteed by default</span>
    max:            {cpu: <span class="gm-s">"64"</span>, memory: <span class="gm-s">"512Gi"</span>, nvidia.com/gpu: <span class="gm-s">"8"</span>}
    min:            {cpu: <span class="gm-s">"1"</span>, memory: <span class="gm-s">"1Gi"</span>}</code></pre>
<div class="gm-note"><b>A subtle trap</b>If a LimitRange gives GPUs a <em>default</em> but a pod doesn't ask for one, it silently receives a GPU. Don't default <code>nvidia.com/gpu</code>; require it explicitly.</div>

## Gang scheduling for multi-node training

<p>A 64-GPU job that gets 60 of them scheduled sits waiting on the last 4 while holding 60 idle. Use Kueue (queues, quotas, fair sharing, all-or-nothing admission) or Volcano/YuniKorn so a job starts only when all its pods can start, and add a <code>PodDisruptionBudget</code> so a routine node upgrade doesn't kill one worker and hang the rest.</p>

## Diagnostic toolkit

<pre><code><span class="gm-c"># GPU health on a node</span>
gpu_health_check() {
  nvidia-smi -q -d MEMORY,UTILIZATION,ECC,TEMPERATURE,POWER,CLOCK,PERFORMANCE
  nvidia-smi pmon -d 5 -c 1                 <span class="gm-c"># which processes on which GPU</span>
  nvidia-smi topo -m
  nvidia-smi nvlink -s                      <span class="gm-c"># NVLink link status/errors</span>
  cat /proc/driver/nvidia/version
  dmesg -T | grep -i xid | tail
}

<span class="gm-c"># GPU visibility inside a pod</span>
debug_gpu_container() {
  local pod=$1
  kubectl exec $pod -- ls -la /dev/nvidia*
  kubectl exec $pod -- env | grep -E <span class="gm-s">"CUDA|NVIDIA"</span>
  kubectl exec $pod -- nvidia-smi -L
  kubectl exec $pod -- cat /sys/fs/cgroup/cpuset.cpus.effective   <span class="gm-c"># pinned cores (cgroup v2)</span>
  kubectl exec $pod -- cat /sys/fs/cgroup/memory.max
  kubectl exec $pod -- cat /sys/fs/cgroup/cpu.stat
}

<span class="gm-c"># Cluster-wide performance snapshot</span>
performance_debug() {
  local ns=$1
  kubectl top pods -n $ns --containers
  kubectl top nodes
  kubectl get events -n $ns --sort-by=.lastTimestamp | grep -E <span class="gm-s">"OOM|MemoryPressure|DiskPressure|TopologyAffinity|Preempt"</span>
  curl -s <span class="gm-s">"http://prometheus:9090/api/v1/query?query=avg by (pod)(DCGM_FI_PROF_SM_ACTIVE{namespace=\"$ns\"})"</span> | jq .data.result
}</code></pre>

## Pre-production checklist

<ul>
<li>Node pools tainted by workload class; production pools accept only Guaranteed, integer-CPU pods.</li>
<li>Static CPU Manager + Topology Manager (restricted or single-numa-node) on GPU pools.</li>
<li>GPU Operator with pinned driver/toolkit versions; canary pool for upgrades.</li>
<li>RDMA verified inside pods (<code>NCCL_DEBUG=INFO</code> shows NET/IB).</li>
<li>Kubelet log rotation, image GC and eviction thresholds set; ephemeral-storage limits on every container.</li>
<li>dcgm-exporter with pod labels; the alert set from Chapter 22; node-exporter disk prediction.</li>
<li>Inference engines expose queue/KV metrics; autoscaling on them with warm pools.</li>
<li>Runbooks for drain, GPU reset, RMA; escalation matrix agreed and on-call rotation staffed.</li>
</ul>
