## Answering a service-management probe

<img src="/diagrams/svc-probes/sequence.svg" alt="Answering a service-management probe" class="doc-diagram doc-diagram-seq" />

<!-- DIAGRAM:sequence:END -->
<details class="ic-probe"><summary><span class="ic-tag">SVC-01</span>Your service has <code>After=postgresql.service</code> but still fails at boot with "connection refused." Why?</summary><div class="ic-answer"><p><code>After=</code> is only ordering, and the database's unit probably reports started before it accepts connections (Type=simple or forking before the listener is ready). Fix both sides: make the app retry its dependency with backoff, and prefer dependencies that use <code>Type=notify</code>. Also check that <code>Wants=</code> or <code>Requires=</code> is present; <code>After=</code> alone doesn't start PostgreSQL.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">SVC-02</span>Why might a service with <code>Restart=on-failure</code> stay dead after crashing a few times?</summary><div class="ic-answer"><p>It hit the start rate limit (default 5 starts in 10 s) and entered <code>failed</code> with <code>start-limit-hit</code>; restarts stop until <code>systemctl reset-failed</code>. Tune <code>StartLimitIntervalSec</code>/<code>StartLimitBurst</code> in <code>[Unit]</code> and set <code>RestartSec</code> so fast crashes don't exhaust the budget. Then fix why it crashes.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">SVC-03</span>How do you change only <code>ExecStart</code> for a packaged unit without editing the vendor file?</summary><div class="ic-answer"><p><code>systemctl edit unit</code> creates a drop-in under <code>/etc/systemd/system/unit.d/</code>. Because <code>ExecStart</code> is a list, write an empty <code>ExecStart=</code> first to clear it, then the new value, then <code>daemon-reload</code>. <code>systemctl cat</code> shows the merged result and survives package upgrades.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">SVC-04</span>A service must bind port 443 but must not run as root.</summary><div class="ic-answer"><p><code>AmbientCapabilities=CAP_NET_BIND_SERVICE</code> with <code>User=</code> set, or lower <code>net.ipv4.ip_unprivileged_port_start</code>, or use systemd socket activation so PID 1 binds and passes the fd. Add <code>NoNewPrivileges=yes</code> and <code>CapabilityBoundingSet=</code> to keep the rest minimal.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">SVC-05</span>What happens between <code>systemctl stop</code> and the process being gone?</summary><div class="ic-answer"><p><code>ExecStop</code> if defined, otherwise <code>KillSignal</code> (SIGTERM) to the cgroup per <code>KillMode</code>; the app should drain and exit 0. After <code>TimeoutStopSec</code> (default 90 s) systemd sends SIGKILL to everything left. A service that takes longer than its timeout to drain loses in-flight work, so set the timeout above the drain deadline and make the drain deadline short.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">SVC-06</span>journald is consuming 30 GB on a host. What is the right fix?</summary><div class="ic-answer"><p>Set <code>SystemMaxUse=</code> and <code>SystemKeepFree=</code> in <code>journald.conf</code> and restart journald; vacuum once with <code>journalctl --vacuum-size</code>. Then look at which unit is flooding (<code>journalctl -o json | jq ._SYSTEMD_UNIT | sort | uniq -c</code>) and lower its log level; ship logs off-host so local retention can be short.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">SVC-07</span>Liveness versus readiness: what goes wrong if readiness checks the database?</summary><div class="ic-answer"><p>When the database degrades, every replica goes unready simultaneously, the load balancer has no targets, and a partial outage becomes total; you also lose the ability to serve cached or degraded responses. Readiness should reflect this instance's own ability to handle requests; dependency health belongs in metrics and circuit breakers. Liveness must be even simpler: a dependency-checking liveness probe turns a slow backend into a restart storm.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">SVC-08</span>Deploys show a burst of 502s even though every instance passes health checks. Why?</summary><div class="ic-answer"><p>The load balancer keeps sending requests for a few seconds after an instance receives SIGTERM, because deregistration propagates after the process has already closed its listener. Fix the order: fail readiness or deregister first, wait for propagation (a preStop sleep or explicit LB drain), close the listener, then drain in-flight requests with a deadline below the kill timeout, and send <code>Connection: close</code> / GOAWAY to keep-alive clients.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">SVC-09</span>You need to rename a column on a 2 TB table with zero downtime.</summary><div class="ic-answer"><p>Don't rename. Expand: add the new column; deploy code that writes both and reads old; backfill in throttled batches; switch reads to new behind a flag; after bake, stop writing old; drop the old column in a separate deploy. Use online DDL for the add and any index, watch replication lag during backfill, and keep every step individually rollback-able.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">SVC-10</span>Describe a canary rollout and what decides whether it proceeds.</summary><div class="ic-answer"><p>Ship to a small slice (1%, one zone) alongside a baseline running the old version on comparable traffic. Compare error rate, latency percentiles, saturation (CPU, memory, GC, queue depth), and business metrics over a bake period long enough to see a signal; automate the comparison and halt on regression. Promote in stages by failure domain; rollback is "stop promotion and route away." The canary is only as good as the metrics and the traffic comparability.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">SVC-11</span>Why are configuration changes as dangerous as code changes, and what do you do about it?</summary><div class="ic-answer"><p>They change behavior instantly, fleet-wide, often without the testing, canarying, or rollback tooling code has, and they're frequently typed by hand. Treat config as code: version it, validate before applying, roll it out progressively by failure domain with automatic halt on SLO regression, and make rollback a one-step operation. Flags should fail safe when the config system is unreachable.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">SVC-12</span>What does socket activation give you operationally?</summary><div class="ic-answer"><p>systemd owns the listening socket, so the service can be restarted or crash and reconnecting clients queue in the backlog instead of getting refused; dependents can start in parallel because the socket exists before the service; rarely used services cost nothing until used. The service receives the fd (<code>LISTEN_FDS</code>) instead of binding.</p></div></details>
