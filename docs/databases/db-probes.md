## How to answer a database probe

<img src="/diagrams/db-probes/sequence.svg" alt="How to answer a database probe" class="doc-diagram doc-diagram-seq" />

<!-- DIAGRAM:sequence:END -->
<details class="ic-probe"><summary><span class="ic-tag">DB-01</span>Replica lag is 40 minutes and growing. What are the likely causes and how do you confirm?</summary><div class="ic-answer"><p>Apply is slower than the primary's write rate: a bulk update or giant transaction, DDL rewriting a table, single-threaded apply, replica I/O or CPU saturation, or long replica queries blocking replay (PostgreSQL conflicts). Confirm with <code>pg_stat_replication</code> lag columns or GTID/heartbeat comparison (not <code>Seconds_Behind_Master</code> alone), replica <code>iostat</code> and CPU, and the primary's recent write pattern. Mitigate by throttling the bulk job, enabling parallel apply, killing conflicting replica queries, and routing reads elsewhere until caught up.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">DB-02</span>Walk through a primary failover and how you avoid split brain.</summary><div class="ic-answer"><p>Quorum-based detection, then fence the old primary (revoke VIP/discovery, kill connections, set read-only or STONITH), promote the most current replica, repoint the remaining replicas, redirect clients through a proxy or service discovery, and handle the reconnect storm with pools and jitter. Split brain is avoided by fencing before promotion and by a single source of truth for leadership (a lease in etcd/Consul as Patroni does).</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">DB-03</span>Why is a pool of 40 connections often faster than 4,000 direct connections to PostgreSQL?</summary><div class="ic-answer"><p>Each connection is a process with memory and scheduler cost, and lock and snapshot bookkeeping grows with connection count, so the database spends time managing connections instead of running queries; beyond the core count, extra concurrency only adds contention. A pool queues work outside the database and keeps it running at its efficient concurrency. PgBouncer transaction mode multiplexes thousands of clients but breaks session state (SET, advisory locks, LISTEN).</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">DB-04</span>Cassandra with RF=3 per DC, LOCAL_QUORUM reads and writes: how many nodes can fail, and what changes at CL=ONE?</summary><div class="ic-answer"><p>Quorum of 3 is 2, so one replica per partition can be down per DC with both availability and strong consistency (R+W=4 &gt; 3). At CL=ONE, two replicas can be down and requests still succeed, but a read may return stale data because it might hit the replica that missed the write; consistency then depends on hints and repair.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">DB-05</span>Reads on one table became slow after a job deleted millions of rows. Why, and what is the relationship between <code>gc_grace_seconds</code> and repair?</summary><div class="ic-answer"><p>Deletes are tombstones that reads must scan through until compaction purges them, which is allowed only after <code>gc_grace_seconds</code>. Purging earlier would let a replica that missed the delete resurrect the data via read repair, so every node must be repaired within that window. Fix the pattern (TTL with TWCS, partition-level deletes, don't use a table as a queue); short-term, compaction after the grace period removes them.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">DB-06</span>Why must a Cassandra query include the partition key, and what is a wide partition?</summary><div class="ic-answer"><p>The partition key determines which nodes hold the data; without it the coordinator would have to scan every node. A wide partition is one key whose rows have grown to hundreds of megabytes or more: it lives entirely on RF nodes, makes those nodes hot, and is slow to read, compact, and repair. Bucket the key (add a time or hash component).</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">DB-07</span>FoundationDB limits transactions to five seconds. Why, and how do you do a long operation?</summary><div class="ic-answer"><p>Storage servers keep about five seconds of versioned history in memory for MVCC reads; older read versions can't be served. Long work is split into many short transactions with explicit continuation (a cursor key), each idempotent and retryable; layers like the Record Layer expose continuations for exactly this.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">DB-08</span>An FDB cluster's throughput dropped and status says "performance limited by storage server." One process is named. Explain.</summary><div class="ic-answer"><p>Ratekeeper throttles the whole cluster to keep the slowest storage server's queue bounded, so one process with a degraded disk, CPU starvation, or a hot shard limits everyone. Check that process's disk latency and queue, look for a hot key range the data distributor hasn't split, and exclude the process to move its shards if the hardware is bad.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">DB-09</span>Kafka: what do <code>acks=all</code> and <code>min.insync.replicas=2</code> guarantee, and what does unclean leader election trade?</summary><div class="ic-answer"><p>An acknowledged write is on at least two replicas, so losing one broker loses nothing acknowledged, and writes fail if fewer than two replicas are in sync (durability over availability). Unclean leader election allows an out-of-sync replica to lead when the ISR is empty, restoring availability while discarding the unreplicated tail: data loss in exchange for uptime.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">DB-10</span>Consumer lag is growing on one topic. Diagnose it.</summary><div class="ic-answer"><p>Compare lag per partition: uniform growth means consumers are too slow or too few (scale to partition count, speed up processing, check for rebalance storms from <code>max.poll.interval.ms</code>); one partition behind means a hot key; a consumer stuck on a poison message shows as zero progress on one partition (dead-letter it). Check broker health and whether lag is approaching retention, at which point it becomes data loss.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">DB-11</span>How do you prevent a cache stampede on a hot key?</summary><div class="ic-answer"><p>Coalesce concurrent misses so one request recomputes while others wait or get stale data; refresh probabilistically before expiry; add TTL jitter so keys don't expire together; and bound the miss path with a rate limit so the database survives a cold cache.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">DB-12</span>A query that has run for months suddenly takes 30× longer. No code changed.</summary><div class="ic-answer"><p>Plan flip (statistics changed or the table crossed a size threshold), lock waits behind a long transaction, bloat or long undo history, cache eviction as the working set grew, autovacuum lagging, disk latency, or a parameter with unusual cardinality. Compare the current plan with <code>EXPLAIN ANALYZE</code>, check <code>pg_stat_activity</code>/innodb_trx for waits, dead tuples, and buffer hit ratio, and fix the cause rather than adding a hint.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">DB-13</span>What is the harm in connections sitting "idle in transaction"?</summary><div class="ic-answer"><p>They hold locks other sessions wait on, hold a snapshot that prevents VACUUM from reclaiming dead rows (bloat, eventual wraparound risk), and pin pool slots. Set <code>idle_in_transaction_session_timeout</code>, fix the application path that opens a transaction and then does slow work, and alert on old transactions.</p></div></details>
<details class="ic-probe"><summary><span class="ic-tag">DB-14</span>Is exactly-once delivery real?</summary><div class="ic-answer"><p>Within a single system that controls both sides (Kafka transactions, FoundationDB), yes. Across systems it reduces to at-least-once plus idempotent consumers: deduplication keys, idempotent writes, or transactional sinks that commit the offset with the output. Design for retries being safe, and the distinction stops mattering.</p></div></details>
